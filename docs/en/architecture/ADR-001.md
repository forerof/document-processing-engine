# ADR-001 · Engine

- **Status:** Accepted
- **Date:** 2026-09-01

## Context

The current implementation of `document-processing-engine` already provides a processing engine capable of orchestrating a complete document processing pipeline.

Rather than implementing every processing task directly, the Engine coordinates specialized components while preserving the processing state after each completed stage.

This Architectural Decision Record documents the current architecture of the Engine without introducing functional changes.

---

## Decision

The Engine is the component responsible for orchestrating the execution of the document processing pipeline.

In the current implementation, the Engine is represented by the `ElectronicIndexService` class.

Its public entry point is:

```java
ElectronicIndexService.processPendingFiles(folderId, spreadsheetId)
```

This method coordinates the complete execution of the processing pipeline.

The Engine itself does not perform document discovery, external communication or result persistence directly. Instead, it coordinates the execution of the components responsible for those tasks.

---

## Responsibilities

The Engine is responsible for:

- Discovering pending documents.
- Coordinating every processing stage.
- Preserving the processing state after every completed stage.
- Deciding whether a processing stage should be executed.
- Allowing interrupted executions to resume safely.

The Engine is not responsible for:

- Reading documents.
- Communicating with external services.
- Persisting processing state implementations.
- Writing processing results.

Those responsibilities belong to dedicated supporting components.

---

## Permanent Processing Rules

The Engine follows the following processing rules.

### Rule 1 — Avoid unnecessary processing

A processing stage shall not be executed if its expected output already exists.

Example:

```text
pages != null

↓

Do not invoke Cloud Run.
```

---

### Rule 2 — Avoid duplicate persistence

The Engine shall never persist duplicated information.

Example:

```text
sheetRow != null

↓

Do not append the document again.
```

---

### Rule 3 — Persist after every completed stage

The processing state shall be persisted immediately after each successfully completed stage.

This guarantees resumability and traceability.

---

### Rule 4 — Resumable execution

An interrupted execution shall always be able to continue from the last successfully completed stage.

The Engine shall never require restarting the complete pipeline.

---

## Current Architecture

The current implementation of the Engine is organized into four logical responsibilities.

### Orchestration

Responsible for coordinating the execution of the processing pipeline.

Current implementation:

- ElectronicIndexService

### Domain

Represents the business model.

Examples include:

- PdfFile
- ProcessedFileRecord
- ProcessingStatus
- SheetSyncStatus

### Processing State Persistence

Responsible for storing and recovering the processing state.

Current implementation:

- ProcessedFilesRepository

### Infrastructure Components

Responsible for interacting with external technologies required by the processing pipeline.

Current implementation includes:

- DriveService
- GoogleSheetsService
- CloudRunClient

This ADR intentionally does not define architectural patterns or classifications for these components. Their architectural role will be documented in future Architectural Decision Records.

---

## Consequences

This architecture provides:

- Centralized orchestration.
- Separation of responsibilities.
- Idempotent execution.
- Safe execution recovery.
- Independent evolution of supporting components.

Future architectural decisions may redefine the interaction between the Engine and infrastructure components without changing the Engine's responsibilities.

---

## Notes

This ADR documents the current implementation of the Engine.

It does not introduce configuration objects, plugin support, dependency injection or infrastructure abstractions.

Those topics will be addressed by future Architectural Decision Records.
