# ADR-001 · Motor

- **Estado:** Aprobado
- **Fecha:** 2026-09-01

## Contexto

La implementación actual de `document-processing-engine` ya dispone de un motor de procesamiento capaz de orquestar un pipeline completo de procesamiento documental.

En lugar de implementar directamente todas las tareas del procesamiento, el Motor coordina componentes especializados mientras preserva el estado del procesamiento después de cada etapa completada.

Este Registro de Decisión Arquitectónica documenta la arquitectura actual del Motor sin introducir cambios funcionales.

---

## Decisión

El Motor es el componente responsable de orquestar la ejecución del pipeline de procesamiento documental.

En la implementación actual, el Motor está representado por la clase `ElectronicIndexService`.

Su punto de entrada público es:

```java
ElectronicIndexService.processPendingFiles(folderId, spreadsheetId)
```

Este método coordina la ejecución completa del pipeline de procesamiento.

El Motor no realiza directamente el descubrimiento de documentos, la comunicación con servicios externos ni la persistencia de resultados. En su lugar, coordina la ejecución de los componentes responsables de dichas tareas.

---

## Responsabilidades

El Motor es responsable de:

- Descubrir los documentos pendientes.
- Coordinar cada etapa del procesamiento.
- Preservar el estado del procesamiento después de cada etapa completada.
- Decidir si una etapa del pipeline debe ejecutarse.
- Permitir reanudar ejecuciones interrumpidas de forma segura.

El Motor no es responsable de:

- Leer documentos.
- Comunicarse con servicios externos.
- Implementar mecanismos concretos de persistencia del estado.
- Escribir los resultados del procesamiento.

Estas responsabilidades pertenecen a componentes de apoyo especializados.

---

## Reglas Permanentes de Procesamiento

El Motor sigue las siguientes reglas de procesamiento.

### Regla 1 — Evitar procesamiento innecesario

Una etapa no debe ejecutarse si el resultado esperado ya existe.

Ejemplo:

```text
pages != null

↓

No consultar Cloud Run.
```

---

### Regla 2 — Evitar persistencia duplicada

El Motor nunca debe persistir información duplicada.

Ejemplo:

```text
sheetRow != null

↓

No volver a insertar el documento.
```

---

### Regla 3 — Persistir después de cada etapa

El estado del procesamiento debe almacenarse inmediatamente después de completar exitosamente cada etapa.

Esto garantiza la reanudación y la trazabilidad del procesamiento.

---

### Regla 4 — Ejecución reanudable

Una ejecución interrumpida siempre debe poder continuar desde la última etapa completada correctamente.

El Motor nunca debe requerir reiniciar el pipeline completo.

---

## Arquitectura Actual

La implementación actual del Motor está organizada en cuatro responsabilidades lógicas.

### Orquestación

Responsable de coordinar la ejecución del pipeline.

Implementación actual:

- ElectronicIndexService

### Dominio

Representa el modelo de negocio.

Entre sus componentes se encuentran:

- PdfFile
- ProcessedFileRecord
- ProcessingStatus
- SheetSyncStatus

### Persistencia del Estado de Procesamiento

Responsable de almacenar y recuperar el estado del procesamiento.

Implementación actual:

- ProcessedFilesRepository

### Componentes de Infraestructura

Responsables de interactuar con las tecnologías externas requeridas por el pipeline.

Actualmente incluyen:

- DriveService
- GoogleSheetsService
- CloudRunClient

Este ADR no define deliberadamente patrones arquitectónicos ni clasificaciones para estos componentes. Su papel arquitectónico será documentado en futuros Registros de Decisión Arquitectónica.

---

## Consecuencias

Esta arquitectura proporciona:

- Orquestación centralizada.
- Separación de responsabilidades.
- Ejecuciones idempotentes.
- Recuperación segura ante interrupciones.
- Evolución independiente de los componentes de apoyo.

Futuras decisiones arquitectónicas podrán redefinir la interacción entre el Motor y los componentes de infraestructura sin modificar las responsabilidades del Motor.

---

## Notas

Este ADR documenta la implementación actual del Motor.

No introduce objetos de configuración, soporte para plugins, inyección de dependencias ni abstracciones de infraestructura.

Estos temas serán abordados en futuros Registros de Decisión Arquitectónica.
